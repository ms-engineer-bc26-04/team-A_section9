# ENKATSU E2Eテストシナリオ

最終更新日：2026/06/30
対象：テスト設計書 7. Frontend手動確認観点（FE-001〜024）
使用ツール：Playwright

## 1. 概要

本ドキュメントは、ENKATSUのFrontend主要導線をPlaywrightでE2Eテスト化した内容をまとめたものです。

未登録ユーザー・一般ユーザー・プレミアムユーザーの3区分について、テスト設計書のFE-001〜024に対応するシナリオを実装しています。

## 2. テストファイル構成

```
frontend/
├── playwright.config.ts
└── e2e/
    ├── auth.setup.ts          ログイン状態を作成し、認証情報を保存する
    ├── guest-user.spec.ts     未登録ユーザーの主要導線（FE-001〜006）
    ├── general-user.spec.ts   一般ユーザーの主要導線（FE-009〜017）
    └── premium-user.spec.ts   プレミアムユーザーの主要導線（FE-019〜024）
```

## 3. 実行環境・前提条件

### 3-1. 必要な準備

- Docker Composeでfrontend（localhost:3000）・backendが起動していること
- `frontend/.env.test.local`（gitignore対象）にテスト用アカウントの認証情報が設定されていること

```
E2E_GENERAL_USER_EMAIL=（一般ユーザーのメールアドレス）
E2E_GENERAL_USER_PASSWORD=（一般ユーザーのパスワード）
E2E_PREMIUM_USER_EMAIL=（プレミアムユーザーのメールアドレス）
E2E_PREMIUM_USER_PASSWORD=（プレミアムユーザーのパスワード）
```

### 3-2. 初回セットアップ

```powershell
cd frontend
npm install
npx playwright install
```

### 3-3. 実行コマンド

```powershell
npm run test:e2e          # 全テスト実行
npm run test:e2e:ui       # UIモードでのデバッグ実行
npm run test:e2e:report   # 直近のHTMLレポート表示
```

特定のテストのみ実行する場合：

```powershell
npm run test:e2e -- -g "FE-013"
```

## 4. 認証の仕組み

Playwrightの`storageState`機能を利用し、テストごとにUIからログインし直す代わりに、事前にログイン済みの状態（Cookie・トークン）をファイルに保存して使い回しています。

| プロジェクト名               | 内容                                                   | 認証状態                             |
| ---------------------------- | ------------------------------------------------------ | ------------------------------------ |
| `setup`                      | `auth.setup.ts`を実行し、2アカウント分の認証状態を保存 | -                                    |
| `chromium`                   | 未登録ユーザー向けテスト（デスクトップ）               | なし                                 |
| `mobile-chrome`              | 未登録ユーザー向けテスト（モバイル）                   | なし                                 |
| `general-user-authenticated` | 一般ユーザー向けテスト                                 | `playwright/.auth/general-user.json` |
| `premium-user-authenticated` | プレミアムユーザー向けテスト                           | `playwright/.auth/premium-user.json` |

`setup`プロジェクトが最初に実行され、他のプロジェクトはこれに依存（`dependencies: ['setup']`）する形になっています。

| ID     | シナリオ                         | 確認内容                                                     |

| FE-019 | マイページでプレミアム表示になる | 「プレミアムユーザー」の表示がされる                         |
| FE-020 | お気に入りを6件以上登録できる    | 上限なく6件登録でき、件数表示に上限がない                    |
| FE-021 | 3園比較できる                    | お気に入りから3園選択し、比較画面へ遷移する                  |
| FE-022 | 希望条件との一致表示が出る       | 比較画面で「あなたの希望条件との一致」セクションが表示される |
| FE-023 | 園詳細でサポート情報が表示される | ロックされず、サポート情報の内容が閲覧できる                 |
| FE-024 | Customer Portalへ遷移できる      | マイページの「変更する」ボタンでポータルへの遷移が開始する   |

備考：

- FE-017・FE-024は、Stripeの実際の決済・ポータル画面までは検証せず、ボタン押下・画面遷移の開始までを確認しています。

## 6. 既知の制約・注意点

### 6-1. バックエンドの並列負荷について

ローカル環境でテストを並列実行すると、バックエンド（Express + Redis）への同時アクセスが集中し、まれにAPIレスポンスが遅延・失敗することがあります。対策として`playwright.config.ts`で以下を設定しています。

- `retries: 1`（失敗時に1回まで自動リトライ）
- `workers`をCPUコア数のデフォルトより少なめに制限

### 6-2. 検索結果・お気に入り件数への依存

お気に入り関連のテストは、検索結果の件数（seedデータ）に依存すると不安定になりやすいため、テスト実行前に状態をリセットしてから必要な件数だけ登録する設計にしています。

### 6-3. UI要素の重なりによるクリック判定

`SchoolCard.tsx`では`FavoriteButton`が`absolute`配置で園詳細へのリンクと重なっているため、クリック位置を指定する（`position: { x: 10, y: 10 }`）ことで誤クリックを回避しています。
