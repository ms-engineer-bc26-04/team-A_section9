# GitHub運用

## 1. 概要

本ドキュメントは、Section9 最終チーム開発における GitHub 運用ルールを整理するためのドキュメントである。

本プロジェクトでは、複数人が同じリポジトリで作業するため、ブランチ運用・Issue作成・PR作成・レビュー・マージ・ドキュメント更新のルールを明確にし、作業の衝突や認識ズレを防ぐ。

---

## 2. 基本方針

- 作業は原則として Issue 単位で管理する
- 実装・修正は原則として `feature/*` ブランチで行う
- PRは原則として `feature/*` から `develop` へ作成する
- `develop` は開発統合ブランチとして扱う
- `staging` はデモ・デプロイ確認用ブランチとして扱う
- `main` は最終提出・安定版として扱う
- 重要な方針変更は、IssueまたはPRコメントに理由を残す

---

## 3. 使用するブランチ

| ブランチ        | 役割                                                  |
| --------------- | ----------------------------------------------------- |
| `main`          | 最終提出・安定版                                      |
| `develop`       | 開発統合用ブランチ                                    |
| `staging`       | デモ・デプロイ確認用ブランチ。RenderのBackendデプロイ対象 |
| `feature/*`     | Issueごとの作業ブランチ                               |
| `fix/*`         | 不具合修正用ブランチ                                  |
| `docs/*`        | ドキュメント修正用ブランチ                            |
| `test/*`        | テスト追加・修正用ブランチ                            |

---

## 4. ブランチ運用

### 4.1 通常開発の流れ

通常開発は以下の流れで行う。

```txt
Issue確認
↓
developを最新化
↓
featureブランチ作成
↓
実装・ドキュメント修正
↓
動作確認・lint確認
↓
PR作成
↓
レビュー
↓
developへマージ
↓
featureブランチ削除
```

---

### 4.2 作業開始時の手順

作業開始前に、必ず `develop` を最新化する。

```bash
git switch develop
git pull origin develop
```

その後、Issue番号を含めた作業ブランチを作成する。

```bash
git switch -c feature/169-deploy-backend
```

---

### 4.3 ブランチ名ルール

```txt
feature/{Issue番号}-{作業内容}
fix/{Issue番号}-{作業内容}
docs/{Issue番号}-{作業内容}
test/{Issue番号}-{作業内容}
```

例：

```txt
feature/10-login-page
feature/169-deploy-backend
fix/153-favorite-compare-auth-test
docs/169-deploy-docs
test/154-e2e-playwright-setup
```

---

### 4.4 developブランチ

`develop` は開発統合用ブランチとして利用する。

- 各作業ブランチは `develop` から作成する
- PRのマージ先は原則として `develop` とする
- `develop` には開発中の最新機能が入る
- `develop` は常に安定していることが望ましいが、実装途中の変更が入る可能性がある

---

### 4.5 stagingブランチ

`staging` はデモ・デプロイ確認用のブランチとして利用する。

Render の Backend デプロイ対象ブランチは `staging` に設定する。

通常開発は `feature/*` → `develop` の流れで行い、デモ環境へ反映したいタイミングで `develop` の内容を `staging` へ反映する。

```bash
git switch staging
git pull origin staging
git merge develop
git push origin staging
```

`staging` へ反映すると、RenderでBackendの自動デプロイが実行される。

#### staging運用の目的

- `develop` に実装中のPRが入っても、デモ環境がすぐに壊れないようにする
- デモで見せたい安定状態だけをデプロイ環境へ反映する
- デプロイ確認・本番相当確認をしやすくする

#### 注意点

- `staging` へ直接作業コミットを積まない
- 原則として `develop` の内容を反映するために使用する
- デモ環境へ反映する前に、`develop` 側で必要な確認を済ませる
- `staging` へ反映した後は、Renderのデプロイ結果を確認する

---

### 4.6 mainブランチ

`main` は最終提出・安定版として利用する。

- 日常的な開発では直接使用しない
- デモ前・提出前など、安定版として反映するタイミングで利用する
- `main` へ反映する場合は、チーム内で確認してから行う

---

### 4.7 軽微な修正の扱い

軽微な修正については、チームで合意したうえで、`feature` ブランチを作成せずに `develop` で直接修正・pushする場合がある。

#### 軽微な修正の例

- READMEの誤字修正
- コメントの軽微な修正
- 表記ゆれの修正
- 明らかなリンク修正
- 実装に影響しない小さなドキュメント修正

#### 注意点

軽微な修正であっても、以下に該当する場合は `feature` ブランチを作成する。

- 画面・API・DBの挙動が変わる
- 複数ファイルに影響する
- レビューが必要な内容
- チーム内で認識合わせが必要な内容
- コンフリクトの可能性が高い内容

---

## 5. 作業中の確認

作業中は、変更内容をこまめに確認する。

```bash
git status
```

必要に応じて差分を確認する。

```bash
git diff
```

---

## 6. コミット運用

コミットメッセージは、日本語の記述で統一する。

### コミットメッセージ例

```bash
git commit -m "技術選定書を追加"
git commit -m "READMEの開発手順を修正"
git commit -m "本番ビルド対象からテストコードを除外"
git commit -m "デプロイ構成をドキュメントに追記"
```

---

## 7. push運用

作業ブランチをリモートへpushする。

```bash
git push origin feature/169-deploy-backend
```

`develop` へ直接pushする場合は、チームで合意済みの軽微な修正に限る。

## 8. Issue運用

### 8.1 Issue作成方針

作業内容はIssueで管理する。

Issueには、目的・背景・対応内容・完了条件を記載し、作業内容を明確にする。

### 8.2 Issue作成時の注意

- 目的を明確に書く
- 作業範囲を広げすぎない
- 完了条件をチェックリストで書く
- 期限がある場合は明記する
- 後続作業がある場合は、別Issueに分ける
- 実装・テスト・ドキュメント整備が混ざりすぎる場合はIssueを分割する

### 8.3 Issueテンプレート例

```md
## 目的

〇〇〇

---

## 背景

〇〇〇

---

## 対応内容

- [ ] 〇〇〇
- [ ] 〇〇〇
- [ ] 〇〇〇

---

## 完了条件

- [ ] 〇〇〇
- [ ] 〇〇〇
```

---

## 9. PR運用

### 9.1 PR作成方針

PRには以下を記載する。

- 概要
- 対応Issue
- 実装・変更内容
- 実装・変更理由
- 確認内容
- 後続Issueで対応する内容
- 補足・注意点

### 9.2 PRの向き

基本は以下とする。

```txt
feature/* → develop
fix/*     → develop
docs/*    → develop
test/*    → develop
```

`main` へ直接PRを出さない。

`staging` へは、デモ環境反映のために `develop` の内容を反映する。

---

### 9.3 PR作成時の注意

- PR本文には対応Issueを記載する
- Issueを自動Closeしたい場合のみ `Closes #Issue番号` を使用する
- 自動Closeしたくない場合は `Refs #Issue番号` を使用する
- 実装内容と確認内容を具体的に記載する
- 画面変更がある場合はスクリーンショットを添付する
- APIやDBに関わる変更がある場合は、関連する設計書の更新有無を確認する
- レビューコメントを確認し、必要に応じて修正する

---

## 10. レビュー運用

### 10.1 レビュー方針

本プロジェクトでは、PR作成後に `@aitutor-review review` を利用してレビューを受ける。

また、AIレビューだけに頼らず、チームメンバーによる確認も行う。

---

### 10.2 AIレビュー

PR作成後、必要に応じて以下のコメントを投稿し、レビューを依頼する。

```txt
@aitutor-review review
```

AIレビューで確認してもらう観点の例：

- 実装内容に大きな問題がないか
- 型定義や責務分離に問題がないか
- ドキュメントの記載に矛盾がないか
- 課題要件から大きく外れていないか
- セキュリティ上の懸念がないか
- 既存機能に影響がないか

---

### 10.3 チームレビュー

`@aitutor-review review` の結果だけに頼らず、チーム内でも内容を確認する。

チームレビューで見る観点：

- Issueの目的を満たしているか
- 画面・API・DB・ドキュメントにズレがないか
- 他メンバーの作業に影響しないか
- チームとして説明しやすい内容になっているか
- デモで見せる際に問題がないか
- コメントを確認して、進捗や修正内容を把握できるか

---

### 10.4 口頭確認とコメント記録

全体方針に関わる内容や、チーム全体で合意した内容については、口頭で確認し合う。

口頭確認した内容は、代表者がPRコメントまたはIssueコメントに残す。

コメントに残す内容の例：

- 方針を決めた理由
- MVP対象に含めるかどうか
- 後続対応に回す理由
- 仕様変更の理由
- チームで合意した内容
- レビューで指摘された内容と対応方針

---

## 11. マージ運用

### 11.1 マージ先

基本的なマージ先は `develop` とする。

```txt
feature/* → develop
```

`main` へは、デモ前や提出前など、安定版としてまとめるタイミングで反映する。

---

### 11.2 マージ前確認

マージ前には以下を確認する。

- 対応Issueが明記されている
- PRテンプレートに沿って記載されている
- 必要なレビューが完了している
- `@aitutor-review review` のコメントを確認している
- GitHub Actionsが通っている
- lint / format / test など、必要な確認が完了している
- 画面変更がある場合はスクリーンショットがある
- ドキュメント変更がある場合はMarkdown表示が崩れていない
- コンフリクトがない

---

### 11.3 マージ後

マージ後は、以下を行う。

- `develop` を最新化する
- 不要になった `feature` ブランチを削除する
- Issueが自動でCloseされているか確認する
- チームにマージ完了を共有する

マージ後のローカル最新化：

```bash
git switch develop
git pull origin develop
```

ブランチ削除例：

```bash
git branch -d feature/51-tech-selection-doc
git push origin --delete feature/51-tech-selection-doc
```

---

## 12. GitHub Actions運用

本プロジェクトでは、`develop` ブランチへの Pull Request 作成時に GitHub Actions を実行する。

### 12.1 確認内容

| 対象     | チェック内容      |
| -------- | ----------------- |
| Frontend | ESLint / Prettier |
| Backend  | ESLint / Prettier |

### 12.2 対応方針

- GitHub Actionsが失敗している場合は、原因を確認して修正する
- Lint / Format エラーは、必要に応じてローカルで修正する
- エラー内容が分からない場合は、チーム内で共有する

---

## 13. デプロイ反映運用

### 13.1 Backend

BackendはRenderにデプロイする。

Render のデプロイ対象ブランチは `staging` とする。

`staging` に変更が入ると、RenderでBackendのデプロイが実行される。

### 13.2 Frontend

FrontendはVercelにデプロイ予定。

Frontendのデプロイ対象ブランチは、デプロイ方針確定後に更新する。

### 13.3 デプロイ反映手順

`develop` の内容をデモ環境へ反映する場合は、以下を実行する。

```bash
git switch staging
git pull origin staging
git merge develop
git push origin staging
```

その後、Renderでデプロイ結果を確認する。

確認内容の詳細は [デプロイ](./デプロイ.md) を参照する。

## 14. ドキュメント運用

### 14.1 管理対象

主なドキュメントは `docs/` 配下で管理する。

| ドキュメント | 目的 |
| ------------ | ---- |
| PRD | プロダクトの目的・背景・価値を整理する |
| 要件定義書 | MVP範囲、機能要件、非機能要件を整理する |
| 画面設計書 | 画面一覧、画面ごとの役割、導線を整理する |
| API設計書 | エンドポイント、リクエスト・レスポンス、認証方針を整理する |
| DB設計書 | テーブル構成、リレーション、削除方針を整理する |
| 性能設計書 | Redisキャッシュ対象API・TTL・キャッシュキー方針を整理する |
| ログ設計書 | ログレベル、出力先、開発・本番でのログ方針を整理する |
| セキュリティ設計書 | XSS、SQL Injection、認証、認可、秘密情報管理を整理する |
| テスト設計書 | 単体テスト・結合テスト・画面確認観点を整理する |
| GitHub運用 | ブランチ、Issue、PR、レビュー、マージ運用を整理する |
| 運用設計書 | Redis・ログ・セキュリティ設定を含む運用確認手順を整理する |
| デプロイ | デプロイ構成、URL、環境変数、確認方法を整理する |

---

### 14.2 更新ルール

- 実装内容とドキュメントにズレが出た場合は、必要に応じてドキュメントを更新する
- 大きな仕様変更がある場合は、IssueまたはPRコメントに理由を残す
- ドキュメント更新時は、Markdownプレビューで表示崩れがないか確認する
- READMEには概要とリンクを中心に記載し、詳細は各docsに記載する

---

## 15. 軽微修正と通常修正の判断基準

| 種類      | 例                                               | ブランチ              |
| --------- | ------------------------------------------------ | --------------------- |
| 軽微修正  | 誤字、リンク修正、コメント修正、表記ゆれ修正     | develop へ直接push可  |
| 通常修正  | 画面追加、API追加、DB変更、設計書の大幅更新      | featureブランチを作成 |
| 要レビュー修正 | 認証認可、データ構造、MVP範囲変更、複数人に影響する内容 | featureブランチを作成しPR |

軽微修正であっても、迷う場合は `feature` ブランチを作成する。

## 16. 完了条件

GitHub運用として、以下が整理されていることを完了条件とする。

- ブランチ運用が整理されている
- `staging` ブランチの役割が整理されている
- Issue運用が整理されている
- PR運用が整理されている
- レビュー運用が整理されている
- マージ運用が整理されている
- GitHub Actions運用が整理されている
- デプロイ反映時のブランチ運用が整理されている
- ドキュメント更新ルールが整理されている

---

## 17. 備考

本ドキュメントは、Section9 最終チーム開発を円滑に進めるための GitHub 運用ルールをまとめたものである。

実際の開発状況やチーム内の合意に応じて、必要に応じて更新する。

運用ルールを変更した場合は、IssueまたはPRコメントに理由を残し、チーム内で共有する。
