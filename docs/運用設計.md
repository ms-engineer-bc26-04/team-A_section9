# 運用設計書

## Redisキャッシュ・ログ・セキュリティ運用確認

### 目的

Redisキャッシュ、Pinoログ、セキュリティ設定について、チームメンバーがローカル環境で確認できるようにする。

また、今後の開発で安全に利用できるように、確認手順・必要な環境変数・運用ルールを整理する。

---

## 必要な環境変数

`backend/.env.example` に以下を記載する。

```env
# Redis
REDIS_URL=redis://redis:6379

# Logging
LOG_LEVEL=debug
```

主な環境変数の役割は以下。

| 変数名       | 内容                            | 例                    |
| ------------ | ------------------------------- | --------------------- |
| REDIS_URL    | Redis接続URL                    | redis://redis:6379    |
| LOG_LEVEL    | Pinoログの出力レベル            | debug                 |
| NODE_ENV     | 実行環境                        | development           |
| FRONTEND_URL | CORSで許可するフロントエンドURL | http://localhost:3000 |

## 起動確認

プロジェクトルートで以下を実行する。

```bash
docker compose up --build
```

別ターミナルでコンテナの起動状態を確認する。

```bash
docker compose ps
```

`backend`、`frontend`、`redis` が起動していればOK。

## Redis疎通確認

Redisに接続できることを確認する。

```bash
docker compose exec redis redis-cli ping
```

以下が返ればOK。

```txt
PONG
```

## Redisキャッシュ確認手順

### 1. Redisの中身を空にする

```bash
docker compose exec redis redis-cli flushall
```

### 2. 園一覧APIを1回実行する

```bash
curl "http://localhost:4000/api/v1/schools"
```

1回目はDBから取得し、Redisに保存される。

### 3. 同じAPIをもう一度実行する

```bash
curl "http://localhost:4000/api/v1/schools"
```

2回目以降はRedisキャッシュから取得される。

### 4. cache miss / cache hit のログを確認する

```bash
docker compose logs backend | grep "schools cache"
```

以下のように `cache miss` と `cache hit` が確認できればOK。

```txt
schools cache miss
schools cache hit
```

## query params 別キャッシュ確認手順

検索条件が異なる場合、別キャッシュとして扱われることを確認する。

```bash
docker compose exec redis redis-cli flushall
```

```bash
curl "http://localhost:4000/api/v1/schools?area=%E6%B8%8B%E8%B0%B7%E5%8C%BA"
curl "http://localhost:4000/api/v1/schools?area=%E6%B8%8B%E8%B0%B7%E5%8C%BA"
```

ログを確認する。

```bash
docker compose logs backend | grep "schools cache"
```

以下のように、`area` 付きのキャッシュキーで `cache miss` と `cache hit` が確認できればOK。

```txt
schools:list?area=%E6%B8%8B%E8%B0%B7%E5%8C%BA
schools cache miss
schools cache hit
```

## Redisキー確認

Redisに保存されたキーを確認する。

```bash
docker compose exec redis redis-cli keys "*"
```

例：

```txt
1) "schools:list"
```

検索条件付きの場合。

```txt
1) "schools:list?area=%E6%B8%8B%E8%B0%B7%E5%8C%BA"
```

TTLを確認する。

```bash
docker compose exec redis redis-cli ttl "schools:list"
```

検索条件付きの場合。

```bash
docker compose exec redis redis-cli ttl "schools:list?area=%E6%B8%8B%E8%B0%B7%E5%8C%BA"
```

`300` 以下の数値が返ればOK。

例：

```txt
(integer) 200
```

## Redis障害時のフォールバック確認

Redisを一時停止する。

```bash
docker compose stop redis
```

Redis停止中に園一覧APIを確認する。

```bash
curl -i "http://localhost:4000/api/v1/schools"
```

`200 OK` が返れば、Redis障害時もDB取得へフォールバックできている。

確認する内容。

- `HTTP/1.1 200 OK` が返ること
- Redis停止中でもDB取得へフォールバックすること
- Redis接続エラーのログが過剰に出続けないこと
- Redis読み取り失敗時は `Redis cache read failed. Fallback to DB.` が出ること

Backendログを確認する。

```bash
docker compose logs -f backend
```

Redis接続関連ログのみ確認する場合。

```bash
docker compose logs backend | grep "Redis"
```

## Redis復旧後の再接続・キャッシュ利用確認

Redisを再起動する。

```bash
docker compose up -d redis
```

Redisが起動していることを確認する。

```bash
docker compose ps
docker compose exec redis redis-cli ping
```

`PONG` が返ればOK。

Backendログを確認する。

```bash
docker compose logs -f backend
```

園一覧APIを複数回実行する。

```bash
curl -i "http://localhost:4000/api/v1/schools"
curl -i "http://localhost:4000/api/v1/schools"
```

以下を確認する。

- Redis復旧後も `GET /api/v1/schools` が `200 OK` を返すこと
- BackendがRedisに再接続できること
- Redis復旧後、再びキャッシュが利用できること
- ログに `schools cache hit` が出ること

既存キャッシュが残っている場合、復旧直後から `schools cache hit` が出ることがある。
`cache miss` から `cache hit` になる流れを明示的に確認したい場合は、Redisのキャッシュを削除してから確認する。

```bash
docker compose exec redis redis-cli FLUSHALL
curl -i "http://localhost:4000/api/v1/schools"
curl -i "http://localhost:4000/api/v1/schools"
```

期待するログ。

```txt
schools cache miss
schools cache hit
```

## Redis再接続・ログ出力方針

Redisはキャッシュ用途であり、Redis停止時もAPI提供を継続する。

そのため、Redis接続エラーは即時のAPI停止要因とはせず、DB取得へフォールバックする。

Redis接続エラー時の運用方針は以下。

- Redis接続に失敗してもAPIレスポンスは継続する
- Redis停止時はDB取得へフォールバックする
- Redis停止中に同じエラーログが過剰に出続けないよう、Redis接続エラーのログ出力頻度を抑制する
- Redis復旧後は再接続し、再びキャッシュを利用できる状態にする
- Redis読み取り失敗時は `Redis cache read failed. Fallback to DB.` を出力する
- Redis書き込み失敗時は `Redis cache write failed. Continue without cache.` を出力する
- Redis復旧後は `schools cache hit` によりキャッシュ利用を確認する

## キャッシュ対象

以下の条件を満たす場合のみ、Redisキャッシュを利用する。

- 匿名ユーザーの `GET /api/v1/schools`
- `sort=recommended` ではないリクエスト
- Redisが利用可能な状態であること

---

## キャッシュ対象外

以下はキャッシュ対象外とする。

- 認証ユーザー向けレスポンス
- `sort=recommended`
- `isFavorited` などユーザーごとに変わる情報
- `favoriteCount`
- `favoriteLimit`
- `isPremium`
- `matchHighlights`

## セキュリティ設定確認

園一覧APIでヘッダーを確認する。

```bash
curl -i "http://localhost:4000/api/v1/schools"
```

確認する主な項目。

```txt
X-Frame-Options: SAMEORIGIN
X-Content-Type-Options: nosniff
Access-Control-Allow-Origin: http://localhost:3000
X-RateLimit-Limit: 1000
```

認証が必要なAPIを未認証で確認する。

```bash
curl -i "http://localhost:4000/api/v1/users/me"
```

未認証の場合、`401 Unauthorized` が返ることを確認する。

## 動作確認済み内容

以下をローカル環境で確認済み。

- `docker compose up --build` で Redis を含む環境が起動すること
- `docker compose exec redis redis-cli ping` で `PONG` が返ること
- `GET /api/v1/schools` が正常にレスポンスを返すこと

- 2回目の同条件リクエストで `schools cache hit` が出ること

- Redisキーを `redis-cli keys "*"` で確認できること
- TTLを `redis-cli ttl` で確認できること
- Redis停止時も `GET /api/v1/schools` が `200 OK` を返すこと
- Redis停止中にエラーログが過剰に出続けないこと
- Redis復旧後、再びキャッシュが利用できること
- Redis復旧後、`schools cache hit` が出ること
- DockerログでPinoログを確認できること
- Helmet / CORS / RateLimit のヘッダーが返ること

## 運用ルール

- キャッシュ対象APIを追加した場合は、性能設計・運用設計に追記する
- キャッシュTTLを変更した場合は、理由と設定値を残す
- ユーザーごとにレスポンスが変わるAPIは安易にキャッシュしない
- 認証ユーザー向けレスポンスをキャッシュする場合は、キャッシュキーにユーザーIDなどを含める
- Redis接続やRedis読み書きに失敗しても、APIレスポンス自体は返せるようにする
- Redis停止中にエラーログが過剰に出続けないようにする
- Redis復旧後は再接続・キャッシュ利用状況を確認する
- 環境変数を追加した場合は、必ず `.env.example` にも追記する
- 本番環境ではアクセストークン、メールアドレス、個人情報、決済情報などをログに出力しない
