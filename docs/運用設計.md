# 運用設計書

## 1. 概要

本ドキュメントは、Section9 最終チーム開発における開発運用ルールを整理するための運用設計書である。

本プロジェクトでは、チームでWebアプリケーションを開発し、提出・デモできる状態まで完成させることを目指す。

チーム開発では、複数人が同じリポジトリで作業するため、ブランチ運用・Issue作成・PR作成・レビュー・マージ・環境構築・ドキュメント更新のルールを明確にし、作業の衝突や認識ズレを防ぐ。

## 4. ブランチ運用

### 4.1 使用するブランチ

本プロジェクトでは、以下のブランチを基本とする。

| ブランチ        | 役割                      |
| ----------- | ----------------------- |
| main        | 安定版。最終的に提出・デモできる状態を管理する |
| develop     | 開発統合用ブランチ               |
| feature/xxx | Issueごとの作業ブランチ          |

### 4.2 基本ルール

基本的な作業は `feature` ブランチで行い、PRを作成して `develop` へマージする。

* 作業は原則として `feature` ブランチで行う
* `feature` ブランチは、最新の `develop` から作成する
* ブランチ名の先頭には、対応するIssue番号を付ける
* `feature` ブランチから `develop` へPRを作成する
* `develop` へマージ後、不要になった `feature` ブランチは削除する
* `main` へは、提出前・デモ前など安定版として反映するタイミングでマージする

### 4.3 ブランチ名ルール

```txt
feature/{Issue番号}-{作業内容}
```

例：

```txt
feature/51-tech-selection-doc
feature/52-operation-design-doc
feature/10-login-page
```

### 4.4 軽微な修正の扱い

軽微な修正については、チームで合意したうえで、`feature` ブランチを作成せずに `develop` で直接修正・pushする場合がある。

#### 軽微な修正の例

* READMEの誤字修正
* コメントの軽微な修正
* 表記ゆれの修正
* 明らかなリンク修正
* 実装に影響しない小さなドキュメント修正

#### 注意点

軽微な修正であっても、以下に該当する場合は `feature` ブランチを作成する。

* 画面・API・DBの挙動が変わる
* 複数ファイルに影響する
* レビューが必要な内容
* チーム内で認識合わせが必要な内容
* コンフリクトの可能性が高い内容

## 5. 開発フロー

基本的な開発フローは以下とする。

```txt
Issue確認
↓
developを最新化
↓
featureブランチ作成
↓
実装・ドキュメント修正
↓
動作確認・lint確認
↓
PR作成
↓
レビュー
↓
developへマージ
↓
featureブランチ削除
↓
必要に応じてmainへ反映
```

### 5.1 作業開始時の手順

作業開始前に、必ず `develop` を最新化する。

```bash
git switch develop
git pull origin develop
```

その後、Issue番号を含めた `feature` ブランチを作成する。

```bash
git switch -c feature/51-tech-selection-doc
```

### 5.2 作業中の確認

作業中は、変更内容をこまめに確認する。

```bash
git status
```

必要に応じて差分を確認する。

```bash
git diff
```

### 5.3 コミット

コミットメッセージは、日本語の記述で統一する。

#### コミットメッセージ例

```bash
git commit -m "技術選定書を追加"
git commit -m "運用設計書を追加"
git commit -m "READMEの開発手順を修正"
```

### 5.4 push

作業ブランチをリモートへpushする。

```bash
git push origin feature/51-tech-selection-doc
```

## 6. Issue運用

### 6.1 Issue作成方針

作業内容はIssueで管理する。

Issueには、担当候補・目的・期限・タスク・完了条件を記載し、作業内容を明確にする。

### 6.2 Issueテンプレート

```md
## 担当候補
- 〇〇さん

## 目的
〇〇〇

## 期限

## タスク
### 〇〇
- [ ] 〇〇〇
- [ ] 〇〇〇

### 〇〇
- [ ] 〇〇〇
- [ ] 〇〇〇

## 完了条件
- [ ] 〇〇〇
- [ ] 〇〇〇
```

### 6.3 Issue作成時の注意

* 目的を明確に書く
* 作業範囲を広げすぎない
* 完了条件をチェックリストで書く
* 期限がある場合は明記する
* 後続作業がある場合は、別Issueに分ける

## 7. PR運用

### 7.1 PR作成方針

本プロジェクトでは、PRテンプレートを作成し、PR作成時に使用する。

PRには以下を記載する。

* 概要
* 関連Issue
* 期限
* 実装・変更内容
* 実装・変更理由
* 確認内容
* 後続Issueで対応する内容
* 補足・注意点

### 7.2 PRテンプレート

```md
## 概要
- 〇〇〇

## 関連Issue
Closes #1

## 期限

## 実装・変更内容
- **〇〇〇**
- 〇〇〇
- 〇〇〇

## 実装・変更理由
- 〇〇〇
- 〇〇〇

## 確認内容（チェックリスト）
### 〇〇〇
- [ ] 〇〇〇
- [ ] 〇〇〇

### その他確認
- [ ] 〇〇〇

## 後続Issueで対応する内容
- 〇〇〇
- 〇〇〇

## 補足・注意点
- 〇〇〇
```

### 7.3 PR作成時の注意

* PRの向きは基本的に `feature` → `develop` とする
* `main` へ直接PRを出さない
* PR本文には `Closes #Issue番号` を記載する
* 実装内容と確認内容を具体的に記載する
* 画面変更がある場合はスクリーンショットを添付する
* APIやDBに関わる変更がある場合は、関連する設計書の更新有無を確認する
* レビューコメントを確認し、必要に応じて修正する

## 8. レビュー運用

### 8.1 レビュー方針

本プロジェクトでは、PR作成後に `@aitutor-review review` を利用してレビューを受ける。

また、AIレビューだけに頼らず、チームメンバーによる確認も行う。

### 8.2 AIレビュー

PR作成後、必要に応じて以下のコメントを投稿し、レビューを依頼する。

```txt
@aitutor-review review
```

AIレビューで確認してもらう観点の例：

* 実装内容に大きな問題がないか
* 型定義や責務分離に問題がないか
* ドキュメントの記載に矛盾がないか
* 課題要件から大きく外れていないか
* セキュリティ上の懸念がないか
* 既存機能に影響がないか

### 8.3 チームレビュー

`@aitutor-review review` の結果だけに頼らず、チーム内でも内容を確認する。

チームレビューで見る観点：

* Issueの目的を満たしているか
* 画面・API・DB・ドキュメントにズレがないか
* 他メンバーの作業に影響しないか
* チームとして説明しやすい内容になっているか
* デモで見せる際に問題がないか
* コメントを確認して、進捗や修正内容を把握できるか

### 8.4 口頭確認とコメント記録

全体方針に関わる内容や、チーム全体で合意した内容については、口頭で確認し合う。

口頭確認した内容は、代表者がPRコメントまたはIssueコメントに残す。

コメントに残す内容の例：

* 方針を決めた理由
* MVP対象に含めるかどうか
* 後続対応に回す理由
* 仕様変更の理由
* チームで合意した内容
* レビューで指摘された内容と対応方針

## 9. マージ運用

### 9.1 マージ先

基本的なマージ先は `develop` とする。

```txt
feature/xxx → develop
```

`main` へは、デモ前や提出前など、安定版としてまとめるタイミングで反映する。

### 9.2 マージ前確認

マージ前には以下を確認する。

* 対応Issueが明記されている
* PRテンプレートに沿って記載されている
* 必要なレビューが完了している
* `@aitutor-review review` のコメントを確認している
* lintやテストなど、必要な確認が完了している
* 画面変更がある場合はスクリーンショットがある
* ドキュメント変更がある場合はMarkdown表示が崩れていない
* コンフリクトがない

### 9.3 マージ後

マージ後は、以下を行う。

* `develop` を最新化する
* 不要になった `feature` ブランチを削除する
* Issueが自動でCloseされているか確認する
* チームにマージ完了を共有する

マージ後のローカル最新化：

```bash
git switch develop
git pull origin develop
```

ブランチ削除例：

```bash
git branch -d feature/51-tech-selection-doc
git push origin --delete feature/51-tech-selection-doc
```

## 11. 環境変数運用

### 11.1 基本方針

環境変数は `.env` で管理し、`.env` はGit管理しない。

共有が必要な項目は `.env.example` に記載する。

### 11.2 方針

* `.env` は各自のローカル環境で作成する
* `.env.example` をもとに必要な値を設定する
* パスワードや秘密鍵をGitHubにpushしない
* 決済・認証・DB・外部APIなどの秘密情報はGit管理しない
* 値を変更した場合は、必要に応じてチームへ共有する
* 実際の秘密情報はGitHub上に記載しない

---

## 12. ログ運用

ログ運用は、今後作成するログ設計書に従う。

### 12.1 基本方針

* フロントエンドはブラウザConsoleに必要最小限のログを出力する
* バックエンドはコンテナの標準出力にログを出力する
* 開発環境と本番環境でログの出し分けを行う
* `password`, `password_hash`, `secret_key`, `token`, `apiKey` などはログ出力しない、またはマスクする
* 本番環境ではデバッグログを出さない

### 12.2 本番環境でのデバッグログ制御

デバッグログは開発・調査時のみ使用する。

本番環境では、環境変数などでログレベルを制御し、DEBUG レベルのログを出力しない方針とする。

例：

```env
NODE_ENV=production
LOG_LEVEL=INFO
```

## 13. セキュリティ運用

本プロジェクトでは、課題要件として以下の観点を考慮する。

* XSS対策
* SQL Injection対策
* 認証・認可
* 秘密情報の管理
* 決済情報の安全な取り扱い
* LLMを利用する場合のプロンプトインジェクション対策

### 13.1 基本方針

* ユーザー入力値は適切にバリデーションする
* DB操作ではORMやプレースホルダを利用し、生SQLの直接組み立てを避ける
* 認証が必要なAPIでは、認証状態を確認する
* 権限が必要な操作では、認可チェックを行う
* 決済処理では、カード情報を自前で保持しない
* APIキーやシークレットは環境変数で管理する
* LLMを利用する場合は、ユーザー入力とシステム指示を分離し、重要処理をLLM判断だけに委ねない

## 14. ドキュメント運用

### 14.1 管理対象

主なドキュメントは `docs/` 配下で管理する。

| ドキュメント  | 目的                            |
| ------- | ----------------------------- |
| 要件定義書   | MVP範囲、機能要件、非機能要件を整理する         |
| 画面設計書   | 画面一覧、画面ごとの役割、導線を整理する          |
| API設計書  | エンドポイント、リクエスト・レスポンス、認証方針を整理する |
| DB設計書   | テーブル構成、リレーション、削除方針を整理する       |
| ログ設計書   | ログレベル、出力先、開発・本番でのログ方針を整理する    |
| 技術選定書   | 採用技術と選定理由を整理する                |
| マイルストーン | 開発フェーズと優先順位を整理する              |
| 運用設計書   | ブランチ、Issue、PR、レビュー、環境運用を整理する  |
| テスト設計書  | 単体テスト・結合テスト・画面確認観点を整理する       |

### 14.2 更新ルール

* 実装内容とドキュメントにズレが出た場合は、必要に応じてドキュメントを更新する
* 大きな仕様変更がある場合は、IssueまたはPRコメントに理由を残す
* ドキュメント更新時は、Markdownプレビューで表示崩れがないか確認する
* プロダクト名・サブタイトル・技術構成が決定したら、本ドキュメント内の空欄を更新する

## 15. チーム内コミュニケーション運用

### 15.1 方針

チーム開発では、作業内容や仕様変更をこまめに共有する。

共有する内容：

* 作業開始時の担当Issue
* 作業中に詰まっていること
* 仕様変更の相談
* PR作成・レビュー依頼
* マージ完了報告
* デモ前の確認事項

### 15.2 仕様変更時の扱い

仕様変更が発生した場合は、以下を確認する。

* MVP範囲に影響するか
* 画面設計書に反映が必要か
* API設計書に反映が必要か
* DB設計書に反映が必要か
* READMEに補足が必要か
* 別Issueとして管理する必要があるか

## 16. 軽微修正と通常修正の判断基準

| 種類      | 例                             | ブランチ              |
| ------- | ----------------------------- | ----------------- |
| 軽微修正    | 誤字、リンク修正、コメント修正、表記ゆれ修正        | develop へ直接push可  |
| 通常修正    | 画面追加、API追加、DB変更、設計書の大幅更新      | featureブランチを作成    |
| 要レビュー修正 | 認証認可、データ構造、MVP範囲変更、複数人に影響する内容 | featureブランチを作成しPR |

軽微修正であっても、迷う場合は `feature` ブランチを作成する。
