## Redisキャッシュ設計

### 目的

園一覧APIのレスポンスを Redis にキャッシュし、同一条件での一覧取得時にDBアクセスを減らす。

MVPでは、アクセス頻度が高い想定の `GET /api/v1/schools` をキャッシュ対象とする。

---

### キャッシュ対象API

| API | 内容 | キャッシュ目的 |
| --- | --- | --- |
| GET /api/v1/schools | 園一覧取得 | 一覧取得時のDBアクセスを減らすため |

---

### キャッシュ対象外

以下はユーザーごとにレスポンスが変わる可能性があるため、MVPではキャッシュ対象外とする。

- ログインユーザー向けの園一覧レスポンス
- `sort=recommended`
- `isFavorited`
- `favoriteCount`
- `favoriteLimit`
- `isPremium`
- `matchHighlights`

ユーザーごとにレスポンスが変わるAPIにキャッシュを適用する場合は、キャッシュキーにユーザーIDなどを含める必要があるため、別途設計してから対応する。

---

### キャッシュキー方針

`GET /api/v1/schools` は検索条件によってレスポンスが変わるため、query params を含めてキャッシュキーを作成する。

例：

```txt
schools:list
schools:list?area=%E6%B8%8B%E8%B0%B7%E5%8C%BA
```

query params が異なるリクエストは、別キャッシュとして扱う。

---

### TTL方針

園データは頻繁に更新されるものではないため、MVPでは短めのTTLを設定する。

現在のTTLは以下。

```txt
300秒
```

TTLは定数として定義し、後から変更しやすい形にする。

---

### Redis障害時の方針

Redis接続やRedis読み書きに失敗しても、APIレスポンス自体は返せるようにする。

Redisが利用できない場合は、DBから直接取得する形にフォールバックする。
